# PROJECT: LUDO — Real-Time Multiplayer 3D Web Game

## 1. YOUR ROLE

Act as a senior full-stack engineer, multiplayer game developer, 3D graphics engineer, UI/UX designer, and software architect.

Build a complete, production-quality, browser-based multiplayer Ludo game for exactly four friends.

This is not a static prototype, UI mockup, or frontend-only demonstration. The application must have a working multiplayer backend, a functional Ludo game engine, real-time synchronization, room management, and a polished 3D gaming experience.

Do not stop after creating the landing page. Implement the complete application.

## 2. PRODUCT VISION

Create a premium online Ludo experience where four friends can play together using a private room.

The game should work as follows:

1. A user visits the website.
2. The user enters a username.
3. The user creates a private room.
4. The application generates a unique six-character room code and invitation link.
5. The host shares the invitation with three friends.
6. Friends join using the invitation link or room code.
7. All four players enter a multiplayer lobby.
8. The host starts the match.
9. All players play the same synchronized Ludo game in real time.
10. The first player to bring all four tokens home wins.

No registration, email verification, or password should be required.

## 6. LUDO GAME ENGINE

This is the highest-priority component.

Implement a complete and independently testable Ludo game engine.

### Board structure

Implement a traditional four-player Ludo board with:

- Four home bases.
- Four tokens per player.
- 52 shared outer-path cells.
- Four player-specific home lanes.
- Four starting positions.
- Safe cells.
- Central finishing area.

Every token must have a well-defined position.

Use a canonical path-coordinate system with player-relative offsets so all four players use the same movement logic.

Do not create four unrelated movement implementations.

### Dice mechanics

- Six-sided dice.
- Dice result generated exclusively by the backend.
- Only the active player can roll.
- Dice rolling animation on the frontend.
- Dice result broadcast to all players.
- A six allows a token to leave its base.
- Rolling a six grants an extra turn.
- Three consecutive sixes forfeit the turn, resetting the consecutive-six counter.
- If the player has no legal moves, automatically pass the turn.
- Enforce all dice and turn rules on the server.

### Token movement

Implement:

- Selecting a legal token.
- Moving according to dice value.
- Entering the board after rolling six.
- Capturing opposing tokens.
- Returning captured tokens to their base.
- Safe-cell protection.
- Entering the home lane.
- Requiring an exact roll to reach the final home position.
- Preventing movement beyond the finishing position.

Tokens must move smoothly between individual board cells.

The server must calculate and validate every movement before broadcasting the resulting state.

### Important rule details

- Tokens cannot capture tokens on safe cells.
- Multiple tokens can occupy a safe cell if permitted by the selected rule implementation.
- A token cannot move if its movement violates the board path.
- A player wins only after all four tokens have reached their final home positions.

Document the rules in a dedicated game-rules module.

## 7. REAL-TIME MULTIPLAYER

Use Socket.IO.

Create a server-authoritative architecture.

The backend must maintain the actual game state.

Suggested socket events:

Client to server:
- create_room
- join_room
- leave_room
- player_ready
- start_game
- roll_dice
- move_token
- request_game_state
- request_rematch

Server to client:
- room_created
- room_joined
- player_joined
- player_left
- lobby_updated
- game_started
- dice_rolled
- token_moved
- turn_changed
- token_captured
- player_disconnected
- player_reconnected
- game_finished
- rematch_started
- game_error

All events must validate the session, room membership, game phase, and player permissions.

Important:

- Do not trust dice results sent by clients.
- Do not trust token positions sent by clients.
- Do not trust player turn information sent by clients.
- Reject invalid or duplicate commands.
- Prevent simultaneous actions from corrupting game state.
- Use atomic game-state transitions.
- Broadcast authoritative state updates to every player.

Use server-generated dice randomness and secure session validation.

## 8. DISCONNECTION AND RECONNECTION

Implement robust reconnection handling.

When a player disconnects:

- Keep their player slot reserved.
- Display disconnected status.
- Start a configurable reconnection countdown.
- Preserve their tokens and game progress.
- Allow them to reconnect using their original guest session.

When they reconnect:

- Restore the current game state.
- Restore their player identity.
- Restore their assigned color.
- Resume normal gameplay.

Do not automatically remove a player just because their browser temporarily loses connection.

If the host disconnects, transfer host privileges to another connected player according to a deterministic rule.

Handle reconnection during both lobby and active gameplay.
